# 雷达收发稳定性深度审查

本文先抛开识别、UI、反制等扩展功能，只看“雷达通信能否在比赛中稳定收、稳态维护、按规则发送”。

依据：

- `rules/RoboMaster 2026 机甲大师高校系列赛通信协议 V2.0.0（20260626）.pdf`
- 当前代码中的主链路：`src/main.cc`
- 当前协议头：`include/radar/libs/librm/src/librm/device/referee/protocol_new_v120.hpp`、`protocol_new_v200.hpp`
- 当前通信封装：`include/referee/*`

## 规则硬约束

从通信协议 V2.0.0 抽出的关键约束：

- 串口参数：8 数据位、1 停止位、无硬件流控、无校验位；电源管理模块和机器人为 `115200` 波特率。
- 帧格式：`SOF(0xA5) + data_length + seq + CRC8 + cmd_id + data + CRC16`。
- 常规链路中 `0x0301` 机器人交互数据：
  - 总数据段长度 118 字节。
  - 内容数据段最大 112 字节。
  - 发送方触发发送，频率上限 `30Hz`。
  - 雷达和哨兵每 1000ms 接收数据上限为 `5120` 字节。
- `0x0305` 小地图接收雷达数据：
  - 数据段长度 48 字节。
  - 发送频率上限 `5Hz`。
  - 坐标单位为 `cm`。
  - 坐标 `x,y` 均为 `0` 时视为未发送该机器人坐标。
- 雷达无线链路：
  - `0x0A01` 对方位置，24 字节，`10Hz`。
  - `0x0A02` 对方血量，12 字节，`10Hz`。
  - `0x0A03` 对方剩余发弹量，10 字节，`10Hz`。
  - `0x0A04` 对方宏观状态，8 字节，`10Hz`。
  - `0x0A05` 对方增益，41 字节，`10Hz`。
  - `0x0A06` 对方干扰波密钥，6 字节，`10Hz`，每字节必须为 ASCII 字母或数字。
- `0x020E` 雷达自主决策信息同步：
  - `bit0-1`：雷达拥有的双倍易伤机会，至多 2。
  - `bit2`：对方是否正在被触发双倍易伤。
  - `bit3-4`：己方加密等级，即对方干扰波难度等级。
  - `bit5`：当前是否可以修改己方密钥。
- `0x0121` 雷达自主决策指令：
  - `radar_cmd` 必须单调递增，且每次只能增加 1，否则非法。
  - `password_cmd=1` 表示修改己方密钥。
  - `password_cmd=2` 表示提交破解出的对方密钥。
  - 密钥 6 字节必须为 ASCII 字母或数字。
  - `password_cmd=2` 每次提交后的 10 秒内再次提交无效。
- ID：
  - 红方雷达 ID 为 `9`。
  - 蓝方雷达 ID 为 `109`。
  - 裁判系统服务器 ID 为 `0x8080`，用于哨兵和雷达自主决策指令。

## 当前最影响稳定性的因素

### 1. `0x0A01` 输入 10Hz，但 `0x0305` 发送上限只有 5Hz（已完成）

已实现：0x0305 5Hz心跳 / 状态过期 / password_cmd=2 FIFO+10s冷却

当前 `MapRobotRelay` 在每次收到 `0x0A01` 时立即发送 `0x0305`。

规则上 `0x0A01` 是 10Hz，`0x0305` 上限是 5Hz。也就是说，若信息波端稳定输入，当前链路天然会以 10Hz 尝试发送 `0x0305`，超过规则上限。

影响：

- 服务器可能丢弃、限流或判定通信异常。
- 即使串口物理带宽足够，也会造成协议层不稳定。
- 发送过快会增加与 `0x0121` 等指令争用同一串口的概率。

建议：

- 给 `0x0305` 增加发送节流，最短间隔 200ms。
- `0x0A01` 只更新最新对方位置状态，发送层按 5Hz 取最新状态打包。
- 若状态未变化，可选择不发或维持 5Hz 心跳，按比赛实测决定。

优先级：P0。

### 2. 缺少“状态新鲜度”判断（已完成）

已实现：0x0305 5Hz心跳 / 状态过期 / password_cmd=2 FIFO+10s冷却

当前结构体维护是“最后一次收到什么就一直保留什么”。例如：

- `has_ground_robot_position_` 一旦收到 `0x020B` 就永久为 true。
- `radar0` 一旦收到 `0x0A01` 就一直作为最新敌方位置。
- TCP 客户端断开后，状态不会自动失效。

规则上 `0x020B` 是 1Hz，`0x0A01~0x0A06` 是 10Hz。稳定系统不能只知道“有没有收到过”，还要知道“最近多久没收到”。

影响：

- 信息波处理端掉线后，仍可能继续使用旧状态。
- 己方位置掉线后，`0x0305` 会混入旧的己方坐标。
- 观测上看似“还在发”，实际是旧数据。

建议：

- 给每类维护结构体加 `last_update_time`。
- 建议超时：
  - `0x0A01~0x0A06`：超过 300-500ms 未更新视为失效。
  - `0x020B/0x020C/0x020E`：超过 2-3s 未更新视为失效。
- 失效后：
  - 坐标类字段置 0，符合“x,y 均 0 视为未发送”。
  - 决策类不再触发新指令。

优先级：P0。

### 3. `0x0121 password_cmd=2` 有 10 秒无效窗口（已完成）

已实现：0x0305 5Hz心跳 / 状态过期 / password_cmd=2 FIFO+10s冷却

当前 8002/8003 两个敌方密钥端口各收到一次后会立即发送 `password_cmd=2`。

规则规定：`password_cmd=2` 每次提交后的 10 秒内再次提交无效。若一级密钥和二级密钥在短时间内相继到达，第二次可能被服务器忽略。

影响：

- 程序日志显示“已发送”，但服务器不接受。
- 如果两个端口设计为一级/二级密钥，当前立即发送策略可能浪费第二次机会。

建议：

- `RadarCommandSender` 层维护 `password_verify_next_allowed_time`。
- 8002/8003 收到密钥后进入待发送队列。
- 到达冷却时间后再发下一条。
- 日志记录 `queued/sent/dropped/ignored_by_cooldown`。

优先级：P0。

### 4. `0x0301` 是全 cmd_id 30Hz 上限，不是每个子内容 30Hz（已完成）

已实现：统一 TX 调度器已接管 0x0301 / 0x0305 主发送路径

规则写明：由于存在多个内容 ID，但整个 `cmd_id` 上行频率最大为 30Hz，需要合理安排带宽。

当前虽然只发送少量 `0x0121`，但后续如果加入 UI、自定义数据或更多子协议，很容易误以为每个子协议都能 30Hz。

影响：

- 多功能合并后，`0x0301` 总频率超限。
- 关键 `0x0121` 可能被低优先级 UI 包挤掉。

建议：

- 建立统一 TX 调度器，而不是各模块直接 `serial.WriteAll()`。
- 调度器按命令分类限频：
  - `0x0305`：5Hz。
  - `0x0301`：总 30Hz。
  - `0x0121`：高优先级。
  - UI/日志/调试类发送：低优先级，可丢弃。

优先级：P1。

### 5. 同步日志 I/O 会阻塞事件循环（部分完成）

已增加运行量化指标，先判断日志影响是否严重

当前日志每次结构体更新都会：

- append `.log`
- trunc 写 `latest/*.json`
- raw bin flush

这对调试很舒服，但比赛稳定性上有隐患。文件系统慢、磁盘被写满、USB 盘抖动都会拖慢单线程 `poll` 循环。

影响：

- TCP/串口读取不及时，内核缓冲堆积。
- 串口解包出现突发丢帧。
- 发送决策延迟变大。

建议：

- 比赛模式下：
  - raw bin 保留但降低 flush 频率。
  - latest 快照降频或关闭。
  - 结构体日志改异步队列。
- 队列必须有上限，满了丢日志，不阻塞通信。

优先级：P1。

### 6. TCP 连接缺少来源约束和心跳/超时（已完成）

已实现：未增加自定义协议；8002/8003 改为直接解完整 0x0A06 协议包

当前 TCP 监听 `0.0.0.0`，任何本机网络可达设备都能连接 8001/8002/8003。`TcpServer::AcceptPending()` 会关闭旧 client，换成新 client。

影响：

- 误连接或扫描会踢掉真正的信息波处理端。
- 8002/8003 是一次性密钥端口，错误连接发送 6 字节垃圾后就会关闭端口，真实密钥再来时已经没有机会。
- 已连接但死掉的 TCP 客户端可能长时间占用连接。

建议：

- `config` 增加允许的 peer IP，至少比赛时不要用 `0.0.0.0` 暴露给整网。
- 8001 信息波端加入心跳或接收超时。
- 8002/8003 收到非法密钥时不要永久完成，除非来源 IP 合法且明确发送完整帧。
- 密钥端口建议定义一个很薄的应用层包：magic + level + 6-byte key + checksum，而不是裸收前 6 字节。

优先级：P1。

### 7. 常规链路中 `0x020B` 的来源需要实机确认（需实机确认）

规则表中 `0x020B` 是“服务器→己方哨兵机器人”，不是明确发给雷达。当前 `0x0305` 组包依赖 `serial_referee.data().ground_robot_position` 作为己方地面机器人位置来源。

影响：

- 如果正式雷达链路收不到 `0x020B`，己方位置会长期为 0。
- 当前程序允许未收到 `0x020B` 时发送，这符合之前的测试需求，但地图上的己方坐标可能缺失。

建议：

- 实机确认雷达 ID 是否能收到 `0x020B`。
- 如果不能，应从己方哨兵/服务器/自定义链路另取己方位置。
- 将 `0x020B` 作为可选数据源，而不是唯一数据源。

优先级：P1。

### 8. 协议版本和帧长度边界

当前主协议 `kRefProtocolFrameMaxLen=128`，适配常规链路最大帧。V200 中存在 `0x0310` 300 字节图传链路数据，若误用同一个 `Referee` 解析图传链路，会被长度检查丢弃。

影响：

- 对当前雷达常规链路不是主要问题。
- 但如果后续把图传链路、自定义客户端链路也塞进同一个 parser，会出现“CRC 正确但永远收不到”的现象。

建议：

- 常规链路 parser 和图传链路 parser 分开。
- `kRefProtocolFrameMaxLen` 不应作为所有链路统一最大值。
- 编译期按 revision/link type 定义最大帧长。

优先级：P2。

### 9. 串口异常当前仍是进程级致命错误（已完成）

已实现：串口读写异常进入 reconnect 状态 / 500ms 自动重连 / 重连期间 TCP 保持运行且发送暂停

当前串口读写失败会抛异常，主程序退出。之前已经避免了无限阻塞，但还没有自动恢复。

影响：

- USB 瞬断、裁判系统重启、设备节点重建会导致程序退出。
- 比赛场景下进程退出比丢几帧更糟。

建议：

- 串口读写异常进入 reconnect 状态。
- 每 500ms 或 1s 重试打开 `/dev/ttyUSB0` 和 fallback。
- 重连期间继续保留 TCP 接收，但暂停发送。
- 恢复后重新开始发送 seq。

优先级：P2。

### 10. CRC 正确不等于业务可信

CRC 只保证当前协议帧传输未损坏，不保证数据语义合理。

还需要业务层校验：

- 坐标范围是否在赛场边界内。
- 血量、发弹量、金币数是否在合理范围内。
- `0x0A06` 是否 ASCII 字母/数字。
- `0x020E` 保留位是否异常。
- `0x0121` 是否满足单调递增和冷却时间。

建议：

- 每个结构体维护时记录 `valid` 和 `reject_reason`。
- 对异常值不直接进入发送组包。
- 日志中区分 `raw_received`、`parsed`、`accepted`、`rejected`。

优先级：P2。

## 当前已做得比较好的点

- 主协议已经按字节流解析，不依赖一次 read 得到完整帧。
- 使用 CRC8 校验帧头、CRC16 校验整帧。
- 解析层已经增加未知命令码和 payload 长度边界保护。
- 串口 fd 已改为非阻塞写，并有写超时。
- 发送 `0x0305` 和 `0x0121` 时已有帧长编译期检查。
- 密钥已限制为 6 字节 ASCII 字母/数字。
- 每次运行有独立日志目录，并保留原始二进制输入。

## 建议落地顺序

第一优先级：

1. 给 `0x0305` 加 5Hz 限频，改为“10Hz 输入更新状态，5Hz 发送最新状态”。（已完成）
   已实现：0x0305 5Hz心跳 / 状态过期 / password_cmd=2 FIFO+10s冷却
2. 给所有关键输入状态加 `last_update_time` 和超时失效。（已完成）
   已实现：0x0305 5Hz心跳 / 状态过期 / password_cmd=2 FIFO+10s冷却
3. 给 `password_cmd=2` 加 10 秒冷却队列。（已完成）
   已实现：0x0305 5Hz心跳 / 状态过期 / password_cmd=2 FIFO+10s冷却

第二优先级：

1. 增加统一 TX 调度器，集中管理 `0x0301` 30Hz 和 `0x0305` 5Hz。（已完成）
2. 将日志写入改成异步、有界、可丢弃。（部分完成）
   比赛模式以原始二进制优先，调试阶段用运行指标量化影响
3. TCP 增加来源 IP 限制、心跳、超时和密钥应用层帧。
   来源IP限制/超时（已完成）
   密钥应用层帧（按当前需求不做）

第三优先级：

1. 串口自动重连。（已完成）
   已实现：串口掉线后后台重试打开设备，TCP 接收和定时任务不中断
2. 常规链路和图传链路 parser 分开。
3. 增加业务值域校验和状态拒绝日志。

## 一个核心判断

当前最容易让雷达通信“不稳定”的并不是串口 CRC 或 TCP 分包，而是规则频率和状态生命周期：

- 输入是 `0x0A01` 的 10Hz。
- 输出 `0x0305` 只能 5Hz。
- 决策 `0x0121` 有单调递增和 10 秒冷却。
- 结构体如果没有过期机制，会把“旧数据”伪装成“稳定数据”。

因此下一轮优化应优先做限频、状态新鲜度和统一发送调度，而不是先上多线程。
